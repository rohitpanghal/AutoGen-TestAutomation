# AI Test Recorder — MVP

Record a manual test pass in Chrome, mark logical steps as you go, and get back a
human-readable test case plus a Playwright TypeScript test — generated by Claude.

## How it works

```
Chrome extension (recorder)
    -> deterministic DOM capture (click / input / select / navigate / mark_step)
    -> POST /api/generate
    -> deterministic locator builder (scopes ambiguous selectors before the LLM sees them)
    -> Claude (single structured call: test case + Playwright code)
    -> written to backend/generated-tests/*.spec.ts
    -> POST /api/heal/:id  (optional)
    -> LangGraph loop: run test -> if failing, Claude diagnoses + patches -> rerun
       -> until passing, a suspected real app bug is flagged, or attempts run out
```

Design choices carried over from planning, and why:

- **Manual "Mark Step" button** instead of asking the AI to infer step boundaries
  from a flat action list — boundaries are ground truth, not a guess.
- **One combined LLM call** (test design + code generation) via a single tool-use
  schema, instead of two separate agents — fewer handoffs, lower latency/cost.
- **Sensitive fields are masked at capture time** (password inputs, and anything
  matching `pass|token|secret|ssn|credit|card|cvv|pin`) — the raw value never
  leaves the browser; the generated test references `process.env.TEST_*` instead.
- **File-based storage** (`backend/data/`, `backend/generated-tests/`) instead of
  Postgres for V1 — matches the roadmap's "don't build the whole system first."
  Swap in a database once tests need to be listed/shared/queried.
- Selector priority enforced via the prompt: `data-testid` > role > label > text >
  CSS, XPath only as a last resort — but for elements the recorder flagged as
  ambiguous (duplicate ids, non-unique role+text), the backend computes the
  **already-scoped** Playwright locator expression itself
  (`services/locatorBuilder.ts`) rather than asking the LLM to reason about
  uniqueness in prose. That turned out necessary in practice: telling Claude
  "don't use a bare `#id` if it's ambiguous" was not reliable, but handing it a
  precomputed, correct locator string to copy verbatim was.
- **Self-healing is explicit, not automatic.** Generating a test never runs it.
  Healing is a separate `POST /api/heal/:id` call (triggered by the **Run &
  Self-Heal** button) so every fix is visible with its diagnosis, rather than
  silently rewriting the test on every generate. The loop also refuses to keep
  "fixing" a test whose failure looks like a real application regression rather
  than a broken selector — see below.

Not included yet (see the roadmap in the design doc): screenshots/video, a UI
for editing generated tests, a database (still file-based for V1).

## Self-healing loop

`POST /api/heal/:id` runs a small [LangGraph](https://langchain-ai.github.io/langgraphjs/)
state machine (`backend/src/services/healingGraph.ts`):

```
run test ─┬─ passed ───────────────────────────────► done
          └─ failed ─┬─ attempts exhausted ─────────► done (needs manual review)
                     └─ Claude diagnoses + patches ─┬─ suspects a real app bug ─► done (needs manual review)
                                                     └─ otherwise ───────────────► run test (loop)
```

Each attempt's pass/fail result and diagnosis is returned in the response and
shown in the popup. Two safety properties matter more than the loop itself:

- **The fixer is told not to weaken assertions to make a test pass.** If the
  Playwright failure output looks like the app genuinely behaves differently
  now (not a stale selector or a missing wait), the model sets
  `likelyRealBug: true`, leaves the code untouched, and the loop stops
  immediately instead of burning attempts mutating a test that isn't the
  problem. This is enforced by prompting only (see the caveat below), not by
  a code-level check — the model's judgment call is surfaced to you as the
  `suspectedRealBug` flag rather than hidden.
- **Every fix lands in the same file you already have open.** `updateGeneratedTest`
  overwrites `generated-tests/<slug>.spec.ts` in place, so `git diff` (once
  this becomes a git repo) shows exactly what the loop changed — nothing is
  silently rewritten in a way you can't review.

Caveat: unlike the selector-uniqueness fix, there is no deterministic check
backing "don't weaken assertions" — that instruction lives in the prompt only,
which the earlier `#dropdownMenuLink` incident showed can be ignored. Treat a
`status: "passed"` result as "worth a diff review before you trust it,"
especially if an assertion's expected text changed between attempts.

## Setup

### 1. Backend

```
cd backend
npm install
cp .env.example .env   # then set ANTHROPIC_API_KEY
npm run dev
```

Runs on `http://localhost:4000`. Health check: `GET /health`.

### 2. Extension

```
cd extension
npm install
npm run build
```

Then in Chrome: `chrome://extensions` → enable Developer mode → **Load unpacked**
→ select the `extension/` folder.

### 3. Record a test

1. Open the target app, click the extension icon, name the test, hit **Start Recording**.
2. Interact with the page normally (click, type, select, navigate).
3. Hit **Mark Step** whenever you've completed a logical step (e.g. "Login", "Open order").
4. Hit **Stop & Generate** — Claude returns a test case summary and Playwright code
   in the popup, and writes `backend/generated-tests/<slug>.spec.ts` to disk.

### 4. Run the generated test

```
cd backend
npx playwright install   # first time only
npm run test:generated
```

Set `TEST_BASE_URL` in `backend/.env` to your app's URL first (used as Playwright's `baseURL`).

### 5. Self-heal a failing test (optional)

Instead of (or after) step 4, click **Run & Self-Heal** in the popup. It calls
`POST /api/heal/:id` with the id returned from generation, which runs
`generated-tests/<slug>.spec.ts` for real, and — if it fails — asks Claude to
diagnose and patch it, then reruns, up to 3 attempts by default. Keep the
popup open while it runs (each attempt is a real Playwright run plus an LLM
call, so it can take a minute or more); closing the popup aborts the in-flight
request since it's a normal `fetch` from the popup's page context.

## Project layout

```
extension/            Manifest V3 Chrome extension (TypeScript, no bundler)
  manifest.json
  src/
    content.ts         DOM event capture -> RecordedAction
    background.ts       recording state, navigation capture
    popup.ts             UI: start/stop/mark-step/generate
    types.d.ts            shared ambient types
  popup/popup.html, popup.css

backend/              Node.js + Fastify + Anthropic SDK + LangGraph
  src/
    index.ts
    routes/generate.ts       POST /api/generate
    routes/recordings.ts     GET /api/recordings/:id
    routes/heal.ts            POST /api/heal/:id
    services/anthropic.ts     structured tool-use calls to Claude (generate + fix)
    services/locatorBuilder.ts  deterministic ambiguity-safe Playwright locators
    services/testRunner.ts      runs one spec file with Playwright, captures output
    services/healingGraph.ts    LangGraph run/fix/retry loop
    services/storage.ts         file-based persistence
  generated-tests/    Playwright output + config
  data/               raw recordings + generation results (gitignored)
```
